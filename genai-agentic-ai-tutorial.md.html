If you are new to AI, read this part first. It is mostly plain explanation, with code only at the end. Every later part builds on these ideas.

0.1 How AI evolved

Traditional AI  →  Machine Learning  →  Deep Learning  →  Generative AI  →  Agentic AI
Stage What it does Simple example
Traditional AI Follows rules written by people "If the order total is over 500, flag it for review"
Machine Learning Learns patterns from data instead of fixed rules A spam filter trained on thousands of emails
Deep Learning Machine learning using large neural networks. Strong at images, speech, and language Face recognition, voice assistants
Generative AI Creates new content: text, code, images ChatGPT writing a C# method
Agentic AI Pursues a goal by reasoning, using tools, and taking actions An assistant that creates your Azure environment and deploys your app

Each stage builds on the one before it. Agentic AI is not a brand new technology. It is a Gen AI model (an LLM) placed inside a loop and given tools.

0.2 What is Generative AI (Gen AI)?

Generative AI is AI that creates new content instead of only analyzing existing data.

It can generate:

Type Examples of tools
Text ChatGPT, Claude, Gemini
Code GitHub Copilot
Documents and chat help Microsoft Copilot
Images DALL-E, Midjourney
Audio and video Speech and video generation tools

How Gen AI works (in simple words)

Most text-based Gen AI runs on a Large Language Model (LLM). Examples: GPT, Claude, Gemini, Llama.

  1. The model is trained on a huge amount of text and code.
  2. During training it learns patterns of language: which words and ideas tend to follow which.
  3. When you give it a prompt, it predicts the most likely next piece of text, then the next, and so on, until it has written a full answer.

It is not looking up a stored answer. It is generating a new one each time, which is why the same question can produce slightly different wording.

Example

Prompt

Write a C# method to reverse a string.

Output

using System.Linq;

public static string Reverse(string value)
{
    return new string(value.Reverse().ToArray());
}

The AI produced code that did not exist in that exact form before. (Note the using System.Linq; line. Reverse() on a string comes from LINQ, and the model's snippet may leave it out. Always read and test generated code.)

Characteristics of Gen AI

Feature What it means
Generates content Creates text, code, images
Prompt driven Needs your instructions to start
Reactive Waits for your input, does not act on its own
Context aware Uses the conversation so far (the history you send it)
Creative Produces new wording and ideas

Real-life example

You ask: "Create a Kubernetes Deployment YAML file."

The Gen AI understands the request, writes the YAML, returns it, and stops.

User  →  Prompt  →  LLM  →  Generated Response  →  (done)

What Gen AI is good at, and where it stops

Good at:

  1. Answering questions
  2. Generating code
  3. Summarizing documents
  4. Explaining concepts

On its own, a plain Gen AI model does not:

  1. Make decisions independently
  2. Run long multi-step workflows
  3. Use tools again and again on its own
  4. Take actions without being prompted

Beginner note: Products like ChatGPT and Copilot now add tools and agent features around the model, so the line between "Gen AI" and "Agentic AI" is blurry in real products. In this guide, "Gen AI" means the model answering a prompt, and "Agentic AI" means the model working in a loop with tools.

0.3 What is Agentic AI?

Agentic AI goes beyond writing content. It works toward a goal.

An AI agent is a system that can:

  1. Understand a goal
  2. Plan the tasks needed
  3. Use tools
  4. Make decisions
  5. Execute actions
  6. Observe the results
  7. Retry or change approach if something fails

A useful way to think about it: an agent behaves more like a digital employee than a chatbot.

The agent loop

Goal
  ↓
Reason     (what should I do next?)
  ↓
Plan       (break the goal into steps)
  ↓
Act        (call a tool)
  ↓
Observe    (read the result)
  ↓
Adjust     (did it work? what now?)
  ↓
Complete the goal   (or loop back to Reason)

This is often called Reason, Act, Observe, or the ReAct pattern.

What one loop looks like in practice

Goal: "Create an AKS cluster."

Reason:  I need a resource group before a cluster. Let me check the subscription first.
Act:     check_subscription()
Observe: Subscription is enabled.
Reason:  Now create the resource group.
Act:     create_resource_group("rg-demo")
Observe: Success.
Reason:  Now create the cluster.
Act:     create_aks_cluster("rg-demo", "aks-demo")
Observe: Error: quota exceeded.
Adjust:  Try a smaller node size or tell the user the quota is the blocker.

The last two lines are what makes it an agent. It saw a failure and changed its behavior instead of stopping.

Gen AI vs Agentic AI: same request, two responses

Generative AI. You ask: "Show me Azure AKS cluster creation steps."

1. Create Resource Group
2. Create AKS Cluster
3. Configure kubectl
...

Done. You still have to do the work.

Agentic AI. You ask: "Create an AKS cluster and deploy my application."

Step 1: Check Azure Subscription
Step 2: Create Resource Group
Step 3: Create AKS Cluster
Step 4: Build Docker Image
Step 5: Push to ACR
Step 6: Deploy to AKS
Step 7: Verify Deployment
Step 8: Report Result

The agent performs the multiple actions needed to reach the objective.

Traditional Copilot vs Agentic Copilot

Traditional Copilot Agentic Copilot
You: "Generate a Dockerfile." You: "Containerize my ASP.NET Core application."
Copilot returns a Dockerfile. Agent: 1. Analyze the project. 2. Create the Dockerfile. 3. Build the image. 4. Run tests. 5. Push to the registry. 6. Create Kubernetes YAML. 7. Deploy.
End of interaction. Goal achieved with minimal further input.

0.4 Core components of an AI agent

An agent has four main parts. Learn these four and every framework will make sense.

1. The LLM (the brain)

The model that does the thinking: it reads the situation, analyzes it, and decides what to do next. Examples: GPT, Claude, Gemini, Llama. A stronger model generally makes better decisions in the loop.

2. Memory

What the agent remembers.

Type What it holds Example
Short-term The current conversation and task "User asked to deploy to AKS"
Long-term Facts stored outside the model and loaded when needed "User prefers AKS and Azure DevOps"

Beginner note: the model itself remembers nothing between calls. "Memory" means your code saves information (in a database or vector store) and sends the relevant parts back with the next request.

3. Tools

Tools are how an agent touches the real world. Examples: Azure CLI, GitHub, a database, web search, email, PowerShell, a REST API.

LLM  →  asks to call Azure CLI  →  your code runs it  →  result returned to the LLM

The model does not run the tool. It asks, and your code runs it (explained in 3.4).

4. Planning

The ability to break a big goal into smaller tasks.

Goal: "Create an Inventory API."

1. Create Entity
2. Create DbContext
3. Create Migration
4. Create Repository
5. Create Service
6. Create API Controller
7. Add Swagger
8. Run Migration

Beginner note: in simple agents the model plans by itself through its instructions. Larger frameworks may add a separate planner component that tracks tasks and progress.

Agent architecture

               ┌───────────┐
               │   User    │
               └─────┬─────┘
                     │ goal
                     ▼
             ┌───────────────┐
             │     Agent     │
             └───────┬───────┘
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
     Memory       Planner        LLM
        └────────────┼────────────┘
                     ▼
              Tool Invocation
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
    Azure CLI      GitHub      Database
                     │
                     ▼
                  Result  (fed back to the agent, loop continues)

0.5 Gen AI vs Agentic AI at a glance

Key point: Agentic AI does not replace Gen AI. It is built on top of it. The LLM is the brain, and the agent is the brain plus memory, tools, and a loop.

A simple analogy

Generative AI = Smart Writer Agentic AI = Employee
You ask "Write a report." "Prepare the monthly sales report."
What happens It writes the report. It collects the data, analyzes it, creates charts, writes the report, and emails stakeholders, without you giving each instruction separately.

In one sentence

Generative AI creates content in response to prompts. Agentic AI pursues goals by reasoning, planning, using tools, taking actions, and adapting until the task is done.

Or shorter: Gen AI = "Answer my question." Agentic AI = "Achieve my objective."

Safety note for beginners: An agent that can create cloud resources or deploy code can also create costs or break things. Real agents need limits: scoped permissions, dry-run modes, approval steps for risky actions, and step limits. Part 8 covers this.

0.7 Hands-on: a simulated DevOps agent (your AKS example, made safe)

This demo turns the AKS scenario into code. Nothing real is created. The "cloud" is a few in-memory sets, so you can run it safely and watch the Reason, Act, Observe loop.

The tools are:

Tool What it pretends to do
check_subscription Confirms the Azure subscription is enabled
create_resource_group Creates a resource group
create_aks_cluster Creates a cluster (fails if the resource group is missing)
deploy_app Deploys an image to the cluster (fails if the cluster is missing)
verify_deployment Reports whether pods are running

Notice that two tools return an error when called in the wrong order. That is deliberate. It lets you see the agent observe a failure and adjust.

Python

import json, os
from openai import OpenAI

client = OpenAI()
MODEL = os.getenv("MODEL", "gpt-4o-mini")

# ---- Fake cloud state. Nothing real is created. ----
cloud = {"resource_groups": set(), "clusters": set(), "deployed": set()}

def check_subscription() -> dict:
    return {"subscription": "demo-subscription", "state": "Enabled"}

def create_resource_group(name: str) -> dict:
    cloud["resource_groups"].add(name)
    return {"ok": True, "resource_group": name}

def create_aks_cluster(resource_group: str, cluster_name: str) -> dict:
    if resource_group not in cloud["resource_groups"]:
        return {"error": f"Resource group '{resource_group}' does not exist. Create it first."}
    cloud["clusters"].add(cluster_name)
    return {"ok": True, "cluster": cluster_name}

def deploy_app(cluster_name: str, image: str) -> dict:
    if cluster_name not in cloud["clusters"]:
        return {"error": f"Cluster '{cluster_name}' does not exist. Create it first."}
    cloud["deployed"].add(image)
    return {"ok": True, "deployed": image, "cluster": cluster_name}

def verify_deployment(cluster_name: str) -> dict:
    return {"cluster": cluster_name, "pods_running": 3 if cloud["deployed"] else 0}

REGISTRY = {f.__name__: f for f in [
    check_subscription, create_resource_group, create_aks_cluster, deploy_app, verify_deployment
]}

# ---- Tell the model what tools exist (name, description, parameters) ----
def tool(name, description, **params):
    return {"type": "function", "function": {
        "name": name,
        "description": description,
        "parameters": {
            "type": "object",
            "properties": {p: {"type": "string", "description": d} for p, d in params.items()},
            "required": list(params),
        },
    }}

TOOLS = [
    tool("check_subscription", "Check that the Azure subscription is enabled."),
    tool("create_resource_group", "Create an Azure resource group.", name="Resource group name"),
    tool("create_aks_cluster", "Create an AKS cluster inside an existing resource group.",
         resource_group="Existing resource group name", cluster_name="New cluster name"),
    tool("deploy_app", "Deploy a container image to an existing AKS cluster.",
         cluster_name="Existing cluster name", image="Container image, for example myapp:1.0"),
    tool("verify_deployment", "Check that the deployment is running.", cluster_name="Cluster name"),
]

SYSTEM = (
    "You are a DevOps agent. Work toward the user's goal step by step using the tools. "
    "Check the subscription first. If a tool returns an error, read it and fix the problem. "
    "When finished, give a short report of what you did."
)

def run_agent(goal: str, max_steps: int = 10) -> str:
    messages = [{"role": "system", "content": SYSTEM}, {"role": "user", "content": goal}]
    for step in range(1, max_steps + 1):
        msg = client.chat.completions.create(model=MODEL, messages=messages, tools=TOOLS).choices[0].message

        if not msg.tool_calls:                    # no more tools needed: the agent is finished
            return msg.content

        messages.append(msg)
        for call in msg.tool_calls:
            args = json.loads(call.function.arguments)
            print(f"[{step}] ACT:     {call.function.name}({args})")
            result = REGISTRY[call.function.name](**args)
            print(f"[{step}] OBSERVE: {result}")
            messages.append({"role": "tool", "tool_call_id": call.id, "content": json.dumps(result)})
    return "Stopped: step limit reached."

print(run_agent("Create an AKS cluster called aks-demo in resource group rg-demo and deploy image myapp:1.0."))

C#

using System.ComponentModel;
using Microsoft.Extensions.AI;
using OpenAI;

IChatClient agent = new ChatClientBuilder(
        new OpenAIClient(Environment.GetEnvironmentVariable("OPENAI_API_KEY")!)
            .GetChatClient("gpt-4o-mini").AsIChatClient())
    .UseFunctionInvocation(configure: c => c.MaximumIterationsPerRequest = 10)   // step limit
    .Build();

// ---- Fake cloud state. Nothing real is created. ----
var resourceGroups = new HashSet<string>();
var clusters = new HashSet<string>();
var deployed = new HashSet<string>();

[Description("Check that the Azure subscription is enabled.")]
string CheckSubscription()
{
    Console.WriteLine("ACT: check_subscription");
    return "Subscription demo-subscription is Enabled.";
}

[Description("Create an Azure resource group.")]
string CreateResourceGroup([Description("Resource group name")] string name)
{
    Console.WriteLine($"ACT: create_resource_group({name})");
    resourceGroups.Add(name);
    return $"Resource group {name} created.";
}

[Description("Create an AKS cluster inside an existing resource group.")]
string CreateAksCluster(
    [Description("Existing resource group name")] string resourceGroup,
    [Description("New cluster name")] string clusterName)
{
    Console.WriteLine($"ACT: create_aks_cluster({resourceGroup}, {clusterName})");
    if (!resourceGroups.Contains(resourceGroup))
        return $"Error: resource group {resourceGroup} does not exist. Create it first.";
    clusters.Add(clusterName);
    return $"Cluster {clusterName} created.";
}

[Description("Deploy a container image to an existing AKS cluster.")]
string DeployApp(
    [Description("Existing cluster name")] string clusterName,
    [Description("Container image, for example myapp:1.0")] string image)
{
    Console.WriteLine($"ACT: deploy_app({clusterName}, {image})");
    if (!clusters.Contains(clusterName))
        return $"Error: cluster {clusterName} does not exist. Create it first.";
    deployed.Add(image);
    return $"Deployed {image} to {clusterName}.";
}

[Description("Check that the deployment is running.")]
string VerifyDeployment([Description("Cluster name")] string clusterName)
{
    Console.WriteLine($"ACT: verify_deployment({clusterName})");
    return $"Cluster {clusterName}: {(deployed.Count > 0 ? 3 : 0)} pods running.";
}

var options = new ChatOptions
{
    Tools =
    [
        AIFunctionFactory.Create(CheckSubscription, "check_subscription"),
        AIFunctionFactory.Create(CreateResourceGroup, "create_resource_group"),
        AIFunctionFactory.Create(CreateAksCluster, "create_aks_cluster"),
        AIFunctionFactory.Create(DeployApp, "deploy_app"),
        AIFunctionFactory.Create(VerifyDeployment, "verify_deployment")
    ]
};

var messages = new List<ChatMessage>
{
    new(ChatRole.System,
        "You are a DevOps agent. Work toward the user's goal step by step using the tools. " +
        "Check the subscription first. If a tool returns an error, read it and fix the problem. " +
        "When finished, give a short report of what you did."),
    new(ChatRole.User,
        "Create an AKS cluster called aks-demo in resource group rg-demo and deploy image myapp:1.0.")
};

var response = await agent.GetResponseAsync(messages, options);
Console.WriteLine(response.Text);

How to read this code (line by line for beginners)

  1. The tool functions are ordinary code. They have no AI in them.
  2. The tool descriptions (the tool(...) helper in Python, [Description] in C#) are what the model reads to decide which tool to use. Clear descriptions mean better decisions.
  3. The system prompt is the agent's job description: its role, its rules, and when it is done.
  4. The loop (explicit in Python, hidden inside UseFunctionInvocation() in C#) repeats: ask the model, run any tools it requested, send the results back, repeat.
  5. The step limit (max_steps, MaximumIterationsPerRequest) stops a confused agent from looping forever.
  6. The ACT and OBSERVE lines let you watch the agent work. Compare them to the Reason, Act, Observe diagram in 0.3.

Try these experiments

  1. Ask for a deploy without mentioning the resource group. Watch whether the agent creates one first or hits an error and recovers.
  2. Change the goal to: "Just tell me the steps to create an AKS cluster." A well-behaved agent may answer in text without calling any tool. That is Gen AI behavior inside an agent.
  3. Remove the line "If a tool returns an error, read it and fix the problem" and compare behavior.
  4. Set the step limit to 2 and see what happens when the task needs more steps.
  5. Add a sixth tool, delete_resource_group, and discuss why it would need a human approval step in a real system.

Trainer tip: This demo is the best "aha" moment for newcomers. Run it live, point at the ACT and OBSERVE lines, and say: "That printed trace is the whole difference between a chatbot and an agent."

0.8 Common beginner questions

Is an agent a different kind of model? No. It is a normal LLM plus instructions, tools, memory, and a loop of your code.

Does the AI actually run Azure CLI or my code? No. It asks for a tool to be called. Your program runs it and returns the result. This is why you control permissions and safety.

Do I need to train my own model? Almost never. You use an existing model through an API and shape its behavior with prompts, your data (RAG), and tools.

Is Agentic AI always better than Gen AI? No. Agents cost more, are slower, and are less predictable. If one prompt answers the question, use one prompt.

Can an agent make mistakes? Yes. It can choose the wrong tool, misread a result, or confidently say something false. That is why we add limits, validation, logging, and human approval for risky actions.

Which language should I learn first, C# or Python? Either works. The concepts are identical, which is why this guide shows both. Use the one your team uses.

Part 1: Generative AI

1.1 Definition

Generative AI is a class of AI models that produce new content (text, code, images, audio, video) by learning patterns from large amounts of training data. A Large Language Model (LLM) is the text-focused kind. It predicts the next piece of text (a token) given everything before it, and by repeating that step it writes whole answers.

1.2 Why it exists and what it gives you

Before LLMs, software handled structured data well (tables, forms, rules) but struggled with unstructured language: emails, contracts, call notes, policies. Rules and keyword matching broke on the endless variety of human wording.

LLMs changed this in three ways:

  1. They understand and produce natural language. You describe a task in plain words instead of writing parsing code.
  2. One model covers many tasks. Summarizing, classifying, extracting, translating, and drafting all use the same model with different instructions.
  3. They can follow instructions they were never explicitly trained on. You change behavior by changing the prompt, not by retraining.

Typical business uses: summarizing documents, drafting replies, extracting fields from text, classifying tickets, answering questions over internal content, generating code, and acting as the reasoning engine inside agents.

1.3 Core concepts, one by one

Tokens

A token is a chunk of text, roughly three quarters of an English word on average. Models read and write tokens, and you are billed per token (input and output are priced separately). Why it matters: cost, speed, and the context limit all depend on token count.

Context window

The maximum number of tokens the model can consider in one request, covering your instructions, the conversation history, any documents you pass in, and the answer. The model has no memory outside this window. If you want it to "remember" something, you must send it again.

Prompt and message roles

A request is a list of messages with roles:

Role Purpose
system Sets behavior, tone, rules, and boundaries. Highest priority instructions.
user The person's request.
assistant Earlier model replies (you send these back to keep a conversation going).
tool Results returned from a function the model asked to call (used in agents).

Temperature and sampling

Temperature controls randomness. Low values (0 to 0.3) give consistent, focused answers, which suits extraction and classification. Higher values (0.7 to 1) give more varied wording, which suits brainstorming. It does not control "creativity" in a deep sense, only how adventurous the next-token choice is.

Hallucination

The model can state something false in a confident tone, because it generates plausible text, not verified facts. This is the main reason RAG exists (Part 2) and the reason you ground answers in sources and add checks.

Prompting, RAG, and fine-tuning: choosing the approach

Approach What changes Use when
Prompt engineering The instructions you send Always start here. Cheap and fast.
RAG The facts you send along with the question The model needs your private or current data.
Fine-tuning The model's weights You need a consistent style or format, or a smaller model doing a narrow task. Not for adding facts.

Trainer tip: A very common student mistake is to say "we need to fine-tune the model on our documents." Nearly always they need RAG. Ask: "Is it a knowledge problem or a behavior problem?"

Embeddings

An embedding turns text into a list of numbers (a vector) so that texts with similar meaning end up close together. This lets you search by meaning instead of keywords. "Reset my password" and "I can't log in" land near each other. Embeddings are the base of RAG.

1.4 Example 1: Your first call

Python

import os
from openai import OpenAI

client = OpenAI()  # reads OPENAI_API_KEY
MODEL = os.getenv("MODEL", "gpt-4o-mini")

response = client.chat.completions.create(
    model=MODEL,
    temperature=0.2,
    messages=[
        {"role": "system", "content": "You are a concise assistant for a healthcare IT team."},
        {"role": "user", "content": "Explain what an API gateway does in 3 sentences."},
    ],
)

print(response.choices[0].message.content)
print("Tokens used:", response.usage.total_tokens)

C#

using Microsoft.Extensions.AI;
using OpenAI;

IChatClient client = new OpenAIClient(Environment.GetEnvironmentVariable("OPENAI_API_KEY")!)
    .GetChatClient("gpt-4o-mini")
    .AsIChatClient();

var messages = new List<ChatMessage>
{
    new(ChatRole.System, "You are a concise assistant for a healthcare IT team."),
    new(ChatRole.User, "Explain what an API gateway does in 3 sentences.")
};

var response = await client.GetResponseAsync(messages, new ChatOptions { Temperature = 0.2f });

Console.WriteLine(response.Text);
Console.WriteLine($"Tokens used: {response.Usage?.TotalTokenCount}");

What to point out to students

  1. The model is stateless. Each call carries the full message list.
  2. IChatClient in C# is a provider-neutral interface. Swap OpenAI for Azure OpenAI or a local model by changing only the line that creates the client. (In older Microsoft.Extensions.AI.OpenAI versions the method is called AsChatClient. It was renamed AsIChatClient.)
  3. Show usage early. Tokens equal money.

1.5 Example 2: Streaming and structured output

Streaming shows tokens as they arrive, which makes apps feel faster.

Python

stream = client.chat.completions.create(
    model=MODEL,
    messages=[{"role": "user", "content": "Write a haiku about audit logs."}],
    stream=True,
)
for chunk in stream:
    delta = chunk.choices[0].delta.content
    if delta:
        print(delta, end="", flush=True)

C#

await foreach (var update in client.GetStreamingResponseAsync("Write a haiku about audit logs."))
{
    Console.Write(update.Text);
}

Structured output means asking for JSON so your code can parse it. Always validate the result, because the model can still return malformed data.

Python

import json

resp = client.chat.completions.create(
    model=MODEL,
    temperature=0,

Part 2: RAG (Retrieval-Augmented Generation)

2.1 Definition

RAG is a pattern where you first retrieve relevant pieces of your own data, then augment the prompt with them, then let the model generate an answer based on that material.

2.2 Why and what

An LLM only knows what was in its training data. It does not know your policies, your product docs, last week's incident report, or a customer's record. It also cannot cite where an answer came from.

RAG fixes this without retraining:

  1. Fresh and private knowledge. Update the document store and answers change immediately.
  2. Fewer hallucinations. The model is told to answer from the supplied text.
  3. Traceability. You can show the source passage for every answer.
  4. Access control. You can filter retrieved content by who is asking.

2.3 The pipeline, step by step

Indexing (done ahead of time)

  1. Load documents (PDF, Word, web pages, database rows).
  2. Clean and chunk them into passages. Chunk size is a trade-off. Too large and retrieval gets vague and costs more tokens. Too small and a chunk loses the context needed to make sense. A common start is 300 to 800 tokens with about 10 to 15 percent overlap.
  3. Embed each chunk into a vector.
  4. Store vectors and the original text (plus metadata such as source, date, and permissions) in a vector store.

Query time (every question)

  1. Embed the question with the same embedding model.
  2. Retrieve the top K most similar chunks (cosine similarity is the usual measure).
  3. Build the prompt: instructions, the retrieved chunks, and the question.
  4. Generate the answer and return it with the sources.

Trainer tip: Draw this as two lanes on a whiteboard: "Before the user arrives" (indexing) and "When the user asks" (querying). Students mix them up constantly.

2.4 Example: A RAG system in about 50 lines

This example keeps vectors in memory so students can see every step. Replace it with a real vector store for production.

Python

import numpy as np
from openai import OpenAI

client = OpenAI()
CHAT_MODEL = "gpt-4o-mini"
EMBED_MODEL = "text-embedding-3-small"

documents = {
    "leave-policy.txt": "Employees receive 20 days of paid leave per year. Unused leave up to 5 days carries over to the next year.",
    "remote-work.txt": "Staff may work remotely up to 3 days per week with manager approval. Core hours are 10:00 to 15:00.",
    "expense-policy.txt": "Expenses above 200 USD need director approval. Receipts must be submitted within 30 days.",
}

def embed(texts):
    result = client.embeddings.create(model=EMBED_MODEL, input=texts)
    vectors = np.array([d.embedding for d in result.data])
    return vectors / np.linalg.norm(vectors, axis=1, keepdims=True)  # normalize

# ---- Indexing ----
chunks = []  # (source, text)
for source, text in documents.items():
    chunks.append((source, text))  # real docs: split into smaller chunks first
index = embed([c[1] for c in chunks])

# ---- Query ----
def retrieve(question, k=2):
    q = embed([question])[0]
    scores = index @ q                       # cosine similarity (vectors are normalized)
    top = np.argsort(scores)[::-1][:k]
    return [(chunks[i], float(scores[i])) for i in top]

def answer(question):
    hits = retrieve(question)
    context = "\n\n".join(f"[{src}] {text}" for (src, text), _ in hits)
    system = (
        "Answer using ONLY the context below. "
        "If the answer is not in the context, say you do not know. "
        "Cite the source name in square brackets."
    )
    resp = client.chat.completions.create(
        model=CHAT_MODEL,
        temperature=0,
        messages=[
            {"role": "system", "content": system},
            {"role": "user", "content": f"Context:\n{context}\n\nQuestion: {question}"},
        ],
    )
    return resp.choices[0].message.content

print(answer("How many days can I work from home?"))
print(answer("What is the dress code?"))   # should say it does not know

2.5 Why RAG fails (and the fixes)

Symptom Likely cause Fix
Right document exists but is not retrieved Poor chunking, or keyword-heavy query Better chunk size, add hybrid search (vector plus keyword), add a reranker
Answer mixes unrelated facts K too high, noisy chunks Lower K, add metadata filters, rerank
Model ignores the context Weak instruction Stronger system prompt, lower temperature
Outdated answers Index not refreshed Scheduled or event-driven re-indexing
Users see data they should not No permission filter Store ACL metadata and filter at retrieval time

2.6 Production building blocks

  1. Vector stores: Azure AI Search, PostgreSQL with pgvector, Elasticsearch, Qdrant, Pinecone, Chroma.
  2. Hybrid search and reranking: combine keyword and vector scores, then re-order the top results with a reranker model.
  3. Query rewriting: have the model rewrite vague follow-ups ("what about contractors?") into standalone queries.
  4. Evaluation: keep a test set of questions with expected source passages. Measure retrieval hit rate and answer correctness before and after every change.
  5. Agentic RAG: let an agent decide when to search, what to search for, and whether to search again (see Part 3).

Part 3: Agentic AI

3.1 Definition

Agentic AI is software where an LLM is given a goal, a set of tools, and the freedom to decide the steps needed to reach that goal. It observes results, adjusts, and continues until it finishes or is stopped. An agent is the unit that does this: model plus instructions plus tools plus memory, running in a loop.

3.2 Why and what

A plain LLM call answers once. It cannot check a database, call an API, or notice that its first attempt failed. Real work is multi-step and depends on live information: "Find the customer's last three orders, see if any shipped late, and draft an apology with a refund offer if so."

Agents exist to handle tasks where:

  1. The steps are not known in advance.
  2. The task needs information or actions outside the model (APIs, databases, files).
  3. The next step depends on the result of the previous one.

Chatbot vs workflow vs agent

Chatbot / single call Workflow (fixed pipeline) Agent
Who decides the steps You You (in code) The model
Predictability High High Lower
Handles open-ended tasks Poor Poor Good
Cost and latency Low Low to medium Higher
Typical use Q and A, summarize Extract, validate, route, store Research, support resolution, ops tasks

Trainer tip: Tell students the rule most experienced teams follow: use the simplest thing that works. If you can write the steps down in advance, build a workflow. Use an agent only when the path genuinely cannot be fixed ahead of time.

3.3 Anatomy of an agent

  1. Model (the brain). Reads the situation and decides what to do next. Stronger models make better decisions in the loop.
  2. Instructions (the role). The system prompt: who the agent is, what it may and may not do, when to stop, how to format results.
  3. Tools (the hands). Functions the agent can call: search, database query, send email, create ticket, run code. Each tool has a name, a description, and a typed parameter schema. The description is what the model reads to decide when to use it, so write it carefully.
  4. Memory.
    • Short-term: the message history in the current run.
    • Long-term: facts stored outside the model (a database or vector store) and loaded when relevant.
  5. Planning and reasoning. Patterns for deciding steps:
    • ReAct: think, act (call a tool), observe, repeat.
    • Plan-and-execute: make a plan first, then carry out each step.
    • Reflection: the agent critiques its own output and revises.
  6. The loop and the stop conditions. Call model, run requested tools, send results back, repeat until the model gives a final answer. Always add a maximum step count, a time limit, and a budget.

3.4 How tool calling works (the key mechanism)

This is the single most important thing to teach. Students often think the model runs the function. It does not.

  1. You send the model the question plus a list of tool definitions.
  2. The model replies, not with an answer, but with a request: "Call get_order_status with order_id = A-1001."
  3. Your code runs the function.
  4. You send the result back as a tool message.
  5. The model reads it and either asks for another tool or writes the final answer.

The model proposes. Your code disposes. That is where you enforce permissions, validation, and approvals.

3.5 Example 3: An agent loop written by hand (Python)

Writing the loop once by hand removes the mystery from every framework you use later.

import json, os
from openai import OpenAI

client = OpenAI()
MODEL = os.getenv("MODEL", "gpt-4o-mini")

# ---- Tools (plain functions) ----
ORDERS = {
    "A-1001": {"status": "Delivered", "promised": "2026-09-10", "delivered": "2026-09-14"},
    "A-1002": {"status": "In transit", "promised": "2026-10-15", "delivered": None},
}

def get_order_status(order_id: str) -> dict:
    return ORDERS.get(order_id, {"error": "Order not found"})

def issue_refund(order_id: str, amount: float) -> dict:
    # In real systems: check permissions, limits, and require approval for large amounts
    if amount > 50:
        return {"error": "Amount above limit. Needs human approval."}
    return {"ok": True, "order_id": order_id, "refunded": amount}

REGISTRY = {"get_order_status": get_order_status, "issue_refund": issue_refund}

# ---- Tool schemas the model sees ----
TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "get_order_status",
            "description": "Look up the status and dates for a customer order.",
            "parameters": {
                "type": "object",
                "properties": {"order_id": {"type": "string", "description": "Order id such as A-1001"}},
                "required": ["order_id"],
            },
        },
    },
    {
        "type": "function",
        "function": {
            "name": "issue_refund",
            "description": "Refund a customer. Only use after confirming the order was late.",
            "parameters": {
                "type": "object",
                "properties": {
                    "order_id": {"type": "string"},
                    "amount": {"type": "number", "description": "Amount in USD"},
                },
                "required": ["order_id", "amount"],
            },
        },
    },
]

SYSTEM = (
    "You are a customer support agent. Check order facts with tools before answering. "
    "Never promise a refund without confirming the order was delivered late. "
    "Be brief and polite."
)

def run_agent(goal: str, max_steps: int = 6) -> str:
    messages = [
        {"role": "system", "content": SYSTEM},
        {"role": "user", "content": goal},
    ]
    for step in range(max_steps):
        resp = client.chat.completions.create(model=MODEL, messages=messages, tools=TOOLS)
        msg = resp.choices[0].message

        if not msg.tool_calls:                 # model is done
            return msg.content

        messages.append(msg)                   # keep the model's tool request in history
        for call in msg.tool_calls:
            args = json.loads(call.function.arguments)
            print(f"  step {step + 1}: {call.function.name}({args})")
            result = REGISTRY[call.function.name](**args)
            messages.append({
                "role": "tool",
                "tool_call_id": call.id,
                "content": json.dumps(result),
            })
    return "Stopped: step limit reached."

print(run_agent("My order A-1001 arrived late. Can I get a 10 dollar refund?"))

3.8 Model Context Protocol (MCP) and tools at scale

Writing every tool by hand does not scale. MCP is an open protocol that lets an agent connect to external tool servers (for example a work-item system, a log platform, or a database) through one standard interface. Tools are discovered at runtime instead of being hard-coded. Both Python and C# have MCP client libraries, and Microsoft Agent Framework supports MCP.

The related A2A (Agent-to-Agent) protocol covers one agent calling another agent across systems. For a first course, mention both and focus on plain tool calling.

Part 4: Event-based agents

4.1 Definition

An event-based (event-driven) agent does not wait for a person to type a prompt. It is triggered by an event: a message arriving on a queue, a webhook call, a file landing in storage, a new ticket, a failed pipeline, an alert, or a schedule.

4.2 Why and what

Most business work starts with something happening, not someone asking. Event-driven agents let AI sit inside existing systems:

  1. A support ticket arrives, so an agent classifies it, drafts a reply, and routes it.
  2. A pipeline fails, so an agent reads the logs and posts a probable cause to the team channel.
  3. A claim document is uploaded, so an agent extracts fields and flags missing information.
  4. Every night at 2 AM, an agent summarizes the day's errors.

Benefits: automation without a human starting it, natural fit with queues and serverless platforms, and easy scaling (add more consumers).

4.3 Design points (explain each one)

Point Why it matters
Trigger Queue (Azure Service Bus, Kafka, RabbitMQ), HTTP webhook, Event Grid, timer, or storage event.
Idempotency Events can be delivered twice. The agent must not refund twice or send two emails. Store processed event ids.
Retries and dead-letter queue Model calls fail and time out. Retry with backoff, then park the event for review.
Guardrails and approvals Nobody is watching live, so risky actions need limits or a human approval step.
Observability Log each event id, tool calls, outcome, tokens, and cost. You will need this to debug at 3 AM.
Rate limiting and cost control An event storm can mean thousands of model calls. Cap concurrency and set budgets.
Stateless handlers Keep state in a database, not in the process, so any instance can handle any event.

4.4 Example 5: Ticket triage agent driven by a queue (Python)

An in-process queue shows the shape. In production, replace it with Service Bus, Kafka, or an Azure Function trigger. The agent code stays the same.

import asyncio, json
from openai import OpenAI

client = OpenAI()
MODEL = "gpt-4o-mini"
processed_ids = set()              # production: a database table

def triage(ticket: dict) -> dict:
    resp = client.chat.completions.create(
        model=MODEL,
        temperature=0,
        response_format={"type": "json_object"},
        messages=[
            {"role": "system", "content":
                "You triage IT tickets. Reply JSON only: "
                "{\"category\": \"access|bug|request|outage\", \"priority\": \"low|medium|high\", \"reply\": str}"},
            {"role": "user", "content": ticket["text"]},
        ],
    )
    return json.loads(resp.choices[0].message.content)

async def worker(name: str, queue: asyncio.Queue):
    while True:
        event = await queue.get()
        try:
            if event["id"] in processed_ids:           # idempotency
                continue
            result = await asyncio.to_thread(triage, event)   # SDK call is blocking
            processed_ids.add(event["id"])
            print(f"[{name}] ticket {event['id']} -> {result['category']}/{result['priority']}")
            if result["priority"] == "high":
                print(f"[{name}] ALERT on-call: {event['text']}")
        except Exception as ex:
            print(f"[{name}] failed {event['id']}: {ex}")   # production: retry, then dead-letter
        finally:
            queue.task_done()

async def main():
    queue = asyncio.Queue()
    workers = [asyncio.create_task(worker(f"w{i}", queue)) for i in range(2)]

    # Simulated events (in real life: webhook or message broker)
    await queue.put({"id": "T-1", "text": "Production claims API is returning 500 for all users."})
    await queue.put({"id": "T-2", "text": "Please add me to the QA Slack channel."})
    await queue.put({"id": "T-1", "text": "Production claims API is returning 500 for all users."})  # duplicate

    await queue.join()
    for w in workers:
        w.cancel()

asyncio.run(main())

Part 5: Multi-agent systems

5.1 Definition

A multi-agent system uses several agents, each with its own role, instructions, and tools, that cooperate to finish a larger task.

5.2 Why and what

One agent with 30 tools and a huge prompt tends to get confused, picks the wrong tool, and is hard to test. Splitting the work gives you:

  1. Focus. Each agent has a short, clear role and a small toolset.
  2. Specialization. Different models per role (a cheap model for classification, a stronger one for reasoning).
  3. Checks and balances. A reviewer agent catches the writer agent's mistakes.
  4. Easier testing and ownership. You can evaluate each agent separately.

Costs: more model calls, more latency, and more places to fail. Do not use multi-agent where a single agent works.

5.3 Orchestration patterns

Pattern How it works Good for
Sequential (pipeline) A then B then C, each passing output forward Draft, review, format
Concurrent (fan-out / fan-in) Several agents work in parallel, results are merged Research from multiple angles, multi-document analysis
Router / handoff A triage agent picks the right specialist and hands over Support desks, helpdesks
Supervisor (manager-workers) A manager agent plans, delegates subtasks, collects results Complex open-ended tasks
Group chat / debate Agents discuss in turns, a moderator decides when done Brainstorming, review panels
Magentic-style (planner with ledger) A planner tracks tasks and progress, and assigns agents dynamically Long, complex goals

5.4 Example 6: Sequential agents with a review loop (Python)

A small helper turns "system prompt plus input" into an agent. Three agents then work in order, and the reviewer can send work back.

from openai import OpenAI

client = OpenAI()
MODEL = "gpt-4o-mini"

def agent(role_prompt: str, task: str, temperature: float = 0.3) -> str:
    resp = client.chat.completions.create(
        model=MODEL,
        temperature=temperature,
        messages=[
            {"role": "system", "content": role_prompt},
            {"role": "user", "content": task},
        ],
    )
    return resp.choices[0].message.content

RESEARCHER = "You are a researcher. List 5 key facts about the topic as short bullet points. No opinions."
WRITER     = "You are a writer. Turn the facts into a 120 word explainer for non-technical staff. Plain language."
REVIEWER   = ("You are a strict reviewer. Check the draft against the facts. "
              "If everything is accurate and clear, reply exactly: APPROVED. "
              "Otherwise list the specific problems.")

def run_pipeline(topic: str, max_rounds: int = 3) -> str:
    facts = agent(RESEARCHER, f"Topic: {topic}")
    draft = agent(WRITER, f"Facts:\n{facts}")

    for round_no in range(max_rounds):
        review = agent(REVIEWER, f"Facts:\n{facts}\n\nDraft:\n{draft}", temperature=0)
        print(f"Round {round_no + 1} review: {review[:80]}...")
        if review.strip().startswith("APPROVED"):
            return draft
        draft = agent(WRITER, f"Facts:\n{facts}\n\nPrevious draft:\n{draft}\n\nFix these issues:\n{review}")
    return draft   # stop after max rounds even if not approved

print(run_pipeline("What is a vector database?"))

5.5 Example 7: Router and parallel agents (Python)

import asyncio, json
from openai import AsyncOpenAI

aclient = AsyncOpenAI()
MODEL = "gpt-4o-mini"

async def ask(system: str, user: str, json_mode: bool = False) -> str:
    kwargs = {"response_format": {"type": "json_object"}} if json_mode else {}
    r = await aclient.chat.completions.create(
        model=MODEL, temperature=0,
        messages=[{"role": "system", "content": system}, {"role": "user", "content": user}],
        **kwargs,
    )
    return r.choices[0].message.content

SPECIALISTS = {
    "billing":   "You are a billing specialist. Answer clearly and offer next steps.",
    "technical": "You are a technical support engineer. Give numbered troubleshooting steps.",
    "general":   "You are a friendly general support agent.",
}

async def router(question: str) -> str:
    out = await ask(
        "Classify the request. Reply JSON only: {\"route\": \"billing|technical|general\"}",
        question, json_mode=True)
    route = json.loads(out).get("route", "general")
    return route if route in SPECIALISTS else "general"     # never trust model output blindly

async def handle(question: str) -> str:
    route = await router(question)
    print(f"Routed to: {route}")
    return await ask(SPECIALISTS[route], question)

async def parallel_review(document: str) -> dict:
    """Fan-out: three reviewers run at the same time, then results are merged."""
    reviewers = {
        "security":   "Review for security risks. 3 bullets max.",
        "compliance": "Review for compliance and privacy concerns. 3 bullets max.",
        "clarity":    "Review for clarity and ambiguity. 3 bullets max.",
    }
    results = await asyncio.gather(*(ask(p, document) for p in reviewers.values()))
    return dict(zip(reviewers.keys(), results))

async def main():
    print(await handle("I was charged twice for my March invoice."))
    print(await parallel_review("Users upload files and we store them in a public bucket for faster access."))

asyncio.run(main())

5.6 The same ideas in C#

using System.Text.Json;
using Microsoft.Extensions.AI;
using OpenAI;

IChatClient client = new OpenAIClient(Environment.GetEnvironmentVariable("OPENAI_API_KEY")!)
    .GetChatClient("gpt-4o-mini").AsIChatClient();

async Task<string> Ask(string system, string user, bool json = false, float temperature = 0f)
{
    var options = new ChatOptions { Temperature = temperature };
    if (json) options.ResponseFormat = ChatResponseFormat.Json;
    var r = await client.GetResponseAsync(
        new[] { new ChatMessage(ChatRole.System, system), new ChatMessage(ChatRole.User, user) }, options);
    return r.Text;
}

// ---- Sequential with review loop ----
const string Researcher = "You are a researcher. List 5 key facts about the topic as short bullet points. No opinions.";
const string Writer     = "You are a writer. Turn the facts into a 120 word explainer for non-technical staff. Plain language.";
const string Reviewer   = "You are a strict reviewer. If the draft is accurate and clear reply exactly: APPROVED. Otherwise list the problems.";

async Task<string> RunPipeline(string topic, int maxRounds = 3)
{
    var facts = await Ask(Researcher, $"Topic: {topic}");
    var draft = await Ask(Writer, $"Facts:\n{facts}", temperature: 0.3f);

    for (int round = 1; round <= maxRounds; round++)
    {
        var review = await Ask(Reviewer, $"Facts:\n{facts}\n\nDraft:\n{draft}");
        Console.WriteLine($"Round {round}: {review[..Math.Min(80, review.Length)]}");
        if (review.Trim().StartsWith("APPROVED")) return draft;
        draft = await Ask(Writer, $"Facts:\n{facts}\n\nPrevious draft:\n{draft}\n\nFix these issues:\n{review}", temperature: 0.3f);
    }
    return draft;
}

// ---- Router ----
var specialists = new Dictionary<string, string>
{
    ["billing"]   = "You are a billing specialist. Answer clearly and offer next steps.",
    ["technical"] = "You are a technical support engineer. Give numbered troubleshooting steps.",
    ["general"]   = "You are a friendly general support agent."
};

async Task<string> Handle(string question)
{
    var routeJson = await Ask("Classify the request. Reply JSON only: {\"route\": \"billing|technical|general\"}", question, json: true);
    var route = JsonDocument.Parse(routeJson).RootElement.GetProperty("route").GetString() ?? "general";
    if (!specialists.ContainsKey(route)) route = "general";      // never trust model output blindly
    Console.WriteLine($"Routed to: {route}");
    return await Ask(specialists[route], question);
}

// ---- Parallel fan-out / fan-in ----
async Task<Dictionary<string, string>> ParallelReview(string document)
{
    var reviewers = new Dictionary<string, string>
    {
        ["security"]   = "Review for security risks. 3 bullets max.",
        ["compliance"] = "Review for compliance and privacy concerns. 3 bullets max.",
        ["clarity"]    = "Review for clarity and ambiguity. 3 bullets max."
    };
    var tasks = reviewers.ToDictionary(r => r.Key, r => Ask(r.Value, document));
    await Task.WhenAll(tasks.Values);
    return tasks.ToDictionary(t => t.Key, t => t.Value.Result);
}

Console.WriteLine(await RunPipeline("What is a vector database?"));
Console.WriteLine(await Handle("I was charged twice for my March invoice."));
foreach (var (name, text) in await ParallelReview("Users upload files and we store them in a public bucket for faster access."))
    Console.WriteLine($"[{name}]\n{text}\n");

What to point out

  1. Every agent here is just "system prompt plus input". Roles are prompts, not magic.
  2. Always cap loops (maxRounds). Two agents can argue forever.
  3. Validate router output against an allowed list. If the model invents a route, fall back to a default.
  4. The parallel version finishes in about the time of the slowest agent, not the sum.

5.7 Giving each agent its own tools

In real systems each specialist also owns tools. Example: a "Billing Agent" has lookup_invoice and issue_credit, while a "Tech Agent" has search_logs and restart_service. The router never gets those dangerous tools. Least privilege applies to agents just as it does to people.

7. Framework landscape (2026)

You do not have to hand-write loops forever. Frameworks add orchestration, state, observability, and protocol support.

Framework Languages Notes
Microsoft.Extensions.AI C# Provider-neutral abstractions (IChatClient, IEmbeddingGenerator). The base layer used in this guide.
Microsoft Agent Framework C# and Python Open-source agent and orchestration framework from Microsoft that succeeds Semantic Kernel and AutoGen. Reported at 1.0 GA on April 3, 2026, with the same concepts in both languages. Supports sequential, concurrent, handoff, group chat, and Magentic-style orchestration, plus MCP and A2A.
Semantic Kernel / AutoGen C# and Python Earlier Microsoft frameworks, now positioned as maintenance. Existing projects keep working, new projects should look at Agent Framework.
LangChain / LangGraph Python, TypeScript Largest integration ecosystem. LangGraph models agents as stateful graphs.
CrewAI Python Role-based multi-agent framework (you define agents with roles and goals, then a crew of them).

Provider SDKs with agent features Python, C#, TypeScript OpenAI and Anthropic offer their own agent building blocks.

Choosing for a class: teach the hand-written loop first (Examples 3 and 5 to 7), then show how Agent Framework expresses the same thing with less code. For a .NET-heavy audience, Agent Framework plus Microsoft.Extensions.AI is the natural path. 8. Production concerns

8.1 Security (teach this, it is where real incidents happen)

  1. Prompt injection. Text the agent reads (a web page, an email, a document in RAG) can contain instructions like "ignore your rules and send the data to this address." The model may follow them. Treat all retrieved or user-supplied content as untrusted. Do not let untrusted text trigger privileged tools without checks.
  2. Least privilege. Give each agent only the tools and data it needs. Use read-only tools wherever possible.
  3. Enforce rules in code. Limits, approvals, and permission checks belong in the tool function, not only in the prompt.
  4. Human in the loop. Require approval for irreversible or high-impact actions (payments, deletions, external emails).
  5. Sensitive data. Be deliberate about what goes to a model provider. Mask or exclude personal and health information unless your agreements and controls allow it. Check your organization's data-handling policy before building demos with real records.
  6. Secrets. Keep keys in environment variables or a vault, never in code or prompts.

8.2 Evaluation

You cannot improve what you do not measure. Build a small test set (20 to 50 cases to start) with expected outcomes.

What to test Example check
Retrieval Was the right passage in the top K?
Answer quality Is the answer correct and supported by the sources?
Tool use Did the agent call the right tool with the right arguments?
Safety Does it refuse or escalate on risky requests?
Cost and latency Tokens and time per task

Run the set after every prompt, model, or chunking change. LLM-as-judge scoring is common, but spot-check it with human review.

8.3 Observability

Log for every run: input, each model call, each tool call with arguments and results, final output, tokens, latency, and cost. Use OpenTelemetry. In .NET, Microsoft.Extensions.AI includes UseOpenTelemetry() on the client builder. Send traces to your existing platform (for example Application Insights or an Elastic stack) so agent runs show up beside normal service telemetry.

8.4 Cost and performance

  1. Use smaller models for simple steps (classification, routing) and stronger ones for reasoning.
  2. Keep prompts short. Send only the chunks you need.
  3. Cache repeated prefixes where your provider supports prompt caching.
  4. Set max_tokens, step limits, and per-run budgets.
  5. Run independent calls in parallel.

8.5 When not to use an agent

If a fixed workflow, a rule, or a single LLM call solves the problem, use that. Agents add cost, delay, and unpredictability. Compliance, finance, and clinical decisions need human review regardless of how good the agent looks. This guide is educational material and not a substitute for legal, security, or compliance review of your own systems.

9. Common mistakes to warn students about

  1. Fine-tuning when RAG is what they need.
  2. Putting every document into the prompt instead of retrieving relevant chunks.
  3. No "I don't know" instruction in RAG, so the model guesses.
  4. Vague tool descriptions, so the agent picks the wrong tool.
  5. No step limit, so an agent loops and burns money.
  6. Trusting model output (routes, JSON, tool arguments) without validation.
  7. Putting safety rules only in the prompt.
  8. Using multi-agent designs for problems a single call would solve.
  9. Skipping evaluation, then being unable to tell whether a change helped.
  10. Demoing with real customer or patient data.

10.3 Quiz (with answers)

  1. Does the model execute the tool function? No. It requests a call. Your code runs it and returns the result.
  2. Why does a model "forget" earlier chat turns if you do not resend them? It is stateless. Only the messages in the current request exist for it.
  3. Knowledge problem or behavior problem: which does RAG address? Knowledge.
  4. Why use the same embedding model for documents and questions? Vectors from different models are not comparable.
  5. Why add a step limit to an agent loop? To prevent endless loops, runaway cost, and stuck runs.
  6. What is idempotency and why does an event-driven agent need it? Processing the same event twice gives the same result as processing it once. Brokers can redeliver events.
  7. Name two reasons to split one agent into several. Focus and smaller toolsets, specialization, review and checks, easier testing.
  8. Why enforce a refund limit in code and not only in the prompt? Prompts can be bypassed through injection or odd phrasing. Code cannot.
  9. What is prompt injection? Untrusted text containing instructions that the model may follow, such as a document telling it to leak data.
  10. When should you choose a workflow over an agent? When the steps are known in advance.
